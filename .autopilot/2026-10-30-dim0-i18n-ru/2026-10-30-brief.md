# Задача: Форк Dim0 + внедрение i18n и русской локализации

## Контекст
Репозиторий-оригинал: https://github.com/vcmf/dim0
Лицензия: MIT (форк и модификация разрешены).
Проект: веб-приложение «думающий холст» с ИИ-агентом (React + TypeScript фронтенд, Python FastAPI бэкенд).
Сейчас в проекте НЕТ i18n — все строки интерфейса захардкожены в .tsx файлах.

## Цель
Создать мой личный форк с полноценной русской локализацией, устроенной так,
чтобы при обновлениях из upstream (Sync fork) конфликтов было минимум.

## Пошаговый план

### Шаг 1. Форк и локальная настройка
1. Сделай форк https://github.com/vcmf/dim0 в мой аккаунт.
2. Склонируй форк локально.
3. Добавь upstream remote:
   `git remote add upstream https://github.com/vcmf/dim0.git`
4. Создай рабочую ветку: `git checkout -b feature/i18n-ru`
5. Изучи структуру проекта (особенно webui/ — там React-фронтенд).
   Определи, где именно лежат текстовые строки интерфейса.

### Шаг 2. Внедрение i18n-фреймворка
1. Установи в webui/ зависимости:
   - `react-i18next`
   - `i18next`
   - `i18next-browser-languagedetector` (для автоопределения языка браузера)
2. Создай структуру локалей:
   webui/src/locales/
     ├── en.json      ← базовая локаль (все ключи на английском)
     └── ru.json      ← русский перевод
3. Настрой i18next:
   - Создай файл `webui/src/i18n.ts` (или `i18n/index.ts` — по конвенции проекта).
   - Инициализируй i18next с fallbackLng: 'en', supportedLngs: ['en', 'ru'],
     detection из localStorage → navigator.
   - Подключи i18n.ts в точке входа приложения (main.tsx / App.tsx).
4. Добавь переключатель языка в UI:
   - Найди в интерфейсе место, где логично разместить переключатель
     (например, в настройках, в сайдбаре или в user-меню).
   - Сделай простой селектор EN / RU с сохранением выбора в localStorage.

### Шаг 3. Извлечение строк (главное — аккуратно и полно)
1. Пройдись по всем .tsx / .ts файлам фронтенда и найди ВСЕ
   пользовательские строки (видимый текст, placeholder'ы, aria-label,
   tooltips, сообщения об ошибках, подтверждения, названия кнопок и меню).
2. Для каждой строки:
   - Придумай осмысленный ключ в нотации `snake_case` с группировкой
     по контексту, например:
       t('sidebar.new_board')
       t('toolbar.add_node')
       t('agent.thinking')
       t('errors.failed_to_load')
       t('dialogs.delete_confirm_title')
   - Добавь ключ в `en.json` с исходным английским текстом.
   - Замени строку в .tsx на вызов `t('...')` через хук `useTranslation()`.
3. НЕ трогай:
   - Технические строки (имена API-эндпоинтов, ключи конфигов,
     CSS-классы, идентификаторы).
   - Строки, которые уходят в LLM как системные промпты (их перевод
     может сломать логику агента) — оставь их как есть или вынеси
     в отдельный файл с комментарием.
4. В конце у тебя должно быть:
   - `en.json` — полный словарь всех строк интерфейса.
   - `ru.json` — тот же набор ключей, но значения на русском
     (переведи все ключи качественно, с учётом UX-контекста:
     кнопки — короткие глаголы, сообщения — вежливые, ошибки — понятные).
5. Если проект использует ESLint-правило против «магических строк» —
   включи его, чтобы новые хардкод-строки не появлялись.

### Шаг 4. Проверка
1. Убедись, что при `en` интерфейс выглядит как оригинал.
2. Переключи на `ru` — все видимые строки должны быть на русском,
   ничего не должно остаться английским (кроме намеренно оставленного).
3. Проверь, что нет ошибок в консоли вида `i18next::translator: missingKey`.
4. Прогони линтер и сборку: `npm run build` (или аналог) должен проходить.
5. Если есть тесты — запусти их, чтобы не сломать существующее поведение.

### Шаг 5. Коммиты и пуш (правильная стратегия для будущих Sync fork)
Оформи изменения серией осмысленных коммитов, чтобы при слиянии
с upstream было проще:
1. `chore(i18n): add react-i18next and setup locale infrastructure`
   → только package.json, i18n.ts, подключение в App, селектор языка.
2. `refactor(i18n): extract UI strings from components to en.json`
   → только правки .tsx (замена строк на t(...)) + заполненный en.json.
   Разбей на несколько коммитов по папкам/компонентам, если файлов много.
3. `feat(i18n): add Russian translation (ru.json)`
   → только ru.json.
4. `docs: add I18N.md with fork sync instructions`
   → инструкция для меня: как обновляться из upstream
     (git fetch upstream → merge/rebase → разрешить конфликты
     только в новых ключах → дописать перевод).

Запушь ветку `feature/i18n-ru` в мой форк и создай Pull Request
в свой же форк (можно merge в main). В описании PR кратко перечисли,
что сделано и какие файлы затронуты.

### Шаг 6. Документация (обязательно)
Создай `I18N.md` в корне репозитория со следующим:
- Как работает i18n в проекте.
- Как добавить новую строку (алгоритм для меня).
- Как обновляться из upstream с минимальными конфликтами:
  * `git fetch upstream && git merge upstream/main`
  * конфликты ожидаются только в .tsx, где появились новые t(...) вызовы,
    и в en.json — их надо просто дополнить в ru.json.
- Как переключить язык в UI.
- Список намеренно НЕ переведённых строк (системные промпты LLM и т.п.)
  с обоснованием.

### Ограничения и правила
- НЕ меняй бизнес-логику и НЕ рефакторь компоненты сверх необходимого
  для i18n — это увеличит конфликты при Sync fork.
- НЕ переводи строки, которые уходят в LLM как часть промптов агента,
  если не уверен, что это безопасно (лучше оставить и задокументировать).
- Соблюдай стиль кода проекта (Prettier/ESLint конфиги уже есть).
- Работай только во фронтенде (webui/). Бэкенд (Python) не трогай,
  если там нет пользовательских сообщений, отдаваемых в UI.
- Если найдёшь в проекте уже существующую зачаточную i18n-инфраструктуру —
  используй её, а не создавай параллельную.

### В конце отчитайся
- Сколько строк извлечено и переведено.
- Какие файлы/компоненты затронуты.
- Что осталось непереведённым и почему.
- Ссылка на PR в моём форке.
- Краткая инструкция: как мне теперь обновляться из upstream.

Начинай. Если на каком-то шаге нужны мои решения (например, где
разместить переключатель языка) — спроси перед тем, как делать.

### 1. Охват: полный
Берём полный охват, как в брифе. Цель — полноценная русская локализация,

Важные уточнения к твоему плану:
- В каждом .tsx меняем ТОЛЬКО строковые литералы на вызовы t('...').
  Разметку, пропсы, логику, импорты, порядок элементов — не трогаем.
  Это критично для будущих Sync fork: чем меньше диффа вокруг строки,
  тем реже конфликт.
- Ключи именуй по контексту компонента/фичи (например,
  `agent.thinking`, `board.delete_confirm`, `settings.language_label`),
  чтобы при появлении нового ключа в upstream я сразу видел,
  куда его класть.
- Английские значения в en.json копируй ВЕРБАТИМ из кода, включая
  пунктуацию и регистр — чтобы при `lng: 'en'` интерфейс был
  побайтово идентичен оригиналу.
- Если в файле строка используется дважды с разным смыслом —
  делай два разных ключа, не переиспользуй один.
- Дублирующиеся технические строки (URL, имена событий, ключи
  localStorage) не извлекаем — оставляем как есть и отмечаем
  в I18N.md как «намеренно не переводится».

«в конфликте оставляем логику из upstream, поверх накатываем t()».

### 1. Терминология: принимаю, с дополнениями
board → доска; note → заметка; link → связь; agent → агент; chat → чат; newsfeed → лента; board element → элемент.
«Холст» — не рабочий термин перевода, а описание продукта в маркетинговом смысле; в UI это слово как перевод чего-либо не используем.

Дополни глоссарий (раздел «Глоссарий» в I18N.md):
canvas (как элемент UI) → холст; workspace → рабочее пространство; toolbar → панель инструментов; sidebar → боковая панель; panel → панель; settings → настройки; template → шаблон; project → проект; mindmap / mind map → майндкарта; node (в майндкарте) → узел; connection / edge → связь; message → сообщение; prompt → запрос (в UI; не «промпт»); user → пользователь; profile → профиль.

Правила:
- Один термин — один перевод во всём интерфейсе. Синонимы в коде приводить к одному термину и фиксировать решение в глоссарии.
- Новые термины дописывать в глоссарий по мере работы, а не решать на месте молча.
- Регистр: sentence case в кнопках, меню и заголовках.
